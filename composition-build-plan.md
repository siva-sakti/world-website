## ⚠ THE ONE PLACE BITS AND COMPOSITIONS COUPLE *(owner-surfaced 2026-09-04: "we have to make sure the way you're building compositions works with the way bits are currently done")*
**Verified facts:** only the **text** bit type has a body at all (drawing = `strokes` jsonb · image/audio/pdf = files · link = url), and that body is **HTML**; the composition's is **JSON**. **In her own terms** *(explained twice before it landed — the plain version, kept because it is the one that worked)*: double-click a text card on a board and type · click ✎ write and type · open a text bit's page and type — **that is the SAME BOX every time**, one piece of code wearing different frames; the composition page becomes the fourth. **So teaching that box checklists means checklists appear in board text cards too — automatically.** Mostly good (board cards get richer free), but it means building the composition's editor IS changing what board text cards can do.

**ONE piece of code IS the writing box** — the `TextBit` component (`src/app/board/[id]/text-bit.tsx`). It is not copied; the SAME code is mounted in three places today — **inside a board's text card** (`board/[id]/card.tsx`) · **on a bit's page** (`bit/[id]/text-workspace.tsx`) · **in quick-write** (`write/quick-write.tsx`) — and the composition page becomes the fourth. **Consequence:** teach that component checklists and checklists exist EVERYWHERE it is mounted, board text-cards included. There is no "only in compositions" without a deliberate choice. **The ruled resolution (§13): the CAPABILITY is shared; what is EXPOSED differs by place** (§13.4's per-frame toolkits) — so at build: add the capability once, choose the exposure per mount.
⭐ **THE CROSS-WINDOW CONTRACT (agreed with the board window 2026-09-04; recorded in BOTH lanes — here and its `board-modes-spec.md` §8):** ① the `variant: 'card' | 'page'` prop lands FIRST, in its own small commit, default `'card'` (every existing mount untouched) ② formatting-bar visibility is exposed as a `showToolbar` prop — the modes build keys it off `variant === 'card' && <its mode gate>`; **this lane never owns or moves the bar logic for cards** ③ **extension registration is SINGLE-OWNED (deepened 2026-09-04, recorded in both lanes — its `editor-formatting-and-file-bit-plan.md`):** ②a registers task-list + table once; the board window's checklist build becomes EXPOSURE on top of that registration, never a second one, and checks whether ②a has landed before starting ④ nothing else collides between the lanes.
**The requirement:** the shared editor must write **HTML when mounted on a bit and JSON when mounted on a composition** — an explicit per-mount setting, never an accident. Its capability set stays shared (§13); only the OUTPUT differs. A test asserts each mount's format. *(Not hard; must be deliberate.)*
**⭐ AND WHY THE FORMATS NEVER ACTUALLY MEET** *(owner, 2026-09-04: "if they're brought in as blocks or if they're hovering, does that cause [a problem]?")* — **no, by construction, and it is her own window ruling (§24.5b) that guarantees it:**
- **A block stores a POINTER, not content.** The composition's document holds `{kind, id, label, form…}` (§32.3); the bit's content stays in the bit, in the bit's own format. At display the app fetches and renders it **exactly as on a board** (§9.6's general rule). A table bit shown in writing = "draw bit #77 here" — the composition's JSON never contains the table's HTML. **No conversion, nothing to sync.**
- **The hover layer touches the document not at all** — those windows float above the page (§26).
- **Editing cannot collide either** — a block's content is edited on the bit's own page (§24.5b), never in place, so a composition never writes into a bit's format.
- **Search:** the composition is findable by the chip's cached NAME; the bit by its own words through its own index. Two indexes, no overlap.
- ⚠ **Export is the ONE place a window becomes a copy** — a rendered export must **inline each block as a snapshot** (the table's HTML, the image, the quote) or the file ships dangling references. Consistent with the ruled *"export is a snapshot"* (§30c). **Build detail, named here so it is not discovered late.**
- ✅ **RESOLVED in the other window's lane (owner-ruled there, 2026-09-04): a table bit's cells live in `body` as HTML** — same column as text, no board_cards change. Everything above works unchanged.

**The ruled sequencing** *(owner asked for the ideal, not a forced fit)*: the ideal end-state is ONE format everywhere, but the reasons JSON won for compositions mostly do not transfer to bits (no chips after the split — flatness · no headings · little structure), and the risk classes are opposite — **her compositions are deletable test data; her bits are the real notebook.** So: composition on JSON now (greenfield, zero risk), and **a bit-format conversion stays its own later, separately-proven project** — after the JSON path has real use behind it.
